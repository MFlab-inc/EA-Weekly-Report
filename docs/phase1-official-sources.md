作成: 2026-08-14／みんかぶFX恒久不使用決定（`docs/open-questions.md` 上位決定）を受けて、統計指標も発言系と同様に公式発表元から収集する。本書は既刊2週（`reference/sample-report_20260808.html`・全29イベント、`scripts/phase0/expected-events.json`）から逆算した**対象発表元の最小リスト**と**実装順**を定める。検収基準1（既刊2週の100%捕捉）は不変。

## 2. 実装方式の提案 — 個別スクレイパーではなく設定駆動フレームワーク

`scripts/checkers/`配下に発表元ごとの専用コードを15本書くのではなく、**共通ハーネス＋`config/official-sources.json`（発表元ごとのURL・抽出ルール・kindマッピングを記述）**の構成を提案します。理由:

- 将来の中銀・国が増えても新規コード追加ではなく設定追加で対応できる
- 各チェッカーの挙動（取得間隔・リトライ・キャッシュ・失敗時WARN）を共通化でき、SPEC §3.6のアクセス設計を1箇所で担保できる
- 開発順序を「サイト構造の実測→config記述」に統一でき、Phase 0のみんかぶ/FF実測と同じ型で進められる

もう1点、実装コストを大きく左右する発見があります。

**B3〜B6の民間指数機関（ISM含むA8も同様）は、多くが年次で固定リリース日程を事前公表しています**（例: ISMは年次スケジュールPDFを公表、Ivey・ADPも月内のほぼ固定曜日）。これらは毎週スクレイピングするのではなく、**年1回の公式年次スケジュールを`config/official-sources.json`に取り込み、対象週との照合だけを週次で行う**方式が構造変化に強く保守コストも低いため、実装時にサイト実測した上でこの方式が使えるか判定することを提案します（判定基準: 発表元が向こう12ヶ月の確定日程を事前公表しているか）。

## 3. 実装順（提案）

1. **サイト実測（Phase 0と同じ型）**: A1〜A9の9元について、みんかぶ/FF実測と同じ手法（Actionsランナー上でのURL取得・構造確認）を行い、各サイトが「構造化フィード（JSON/iCal/RSS/API）」か「HTML表の定期スクレイピングが必要」かを判定する。年次固定日程の可否もここで確認
2. **`config/official-sources.json` 設計＋共通ハーネス実装**: 実測結果をもとにURL・抽出ルール・kindマッピングのスキーマを確定し、`scripts/checkers/`の共通取得・パース基盤を実装
3. **優先度A（A1〜A9）の実装＋既刊2週での照合テスト**: ★★★13件の捕捉を確認。この時点で停止スケジュール機能は完成する
4. **優先度B（B1〜B6）のサイト実測→実装**: 残り8件（★★）を回収し検収基準1（29/29件）を満たす
5. **`config/event-names.json`の実データ照合**: `source_verified: false`の11件（8/3週分。lastweek.json 404のため未照合）を、実際に取得した公式ソースの表記で確認・更新
6. **将来拡張分（officials.json記載だがこの2週には未出現の中銀: ECB・BOE・BOC・SNB）は、共通フレームワークへのconfig追加のみで対応**（優先度A/B完了後、並行運用開始までの間に着手）

## 4. 未解決の実装上の注意点（設計時に解決）

- 国債入札の命名規則（SPEC §4.2「入札=『米{年限}債入札』」）は米国債を前提にしているが、既刊8/3週の実例は**日本のJGB入札**（「10年利付国債（2026年8月債）の入札」）。命名テンプレートは国別に分岐が必要（例: 日本=「{年限}利付国債（{年月}債）の入札」、米国=「米{年限}債入札」）。レンダラー実装時に反映する
- ISM等、優先度Aだが民間発表元のものは、政府統計機関と異なりリリース日程の公式APIがない場合がある。実測でHTML定期確認が必要と判明した場合は取得頻度・キャッシュ設計をSPEC §3.6の週次原則内で個別検討する
