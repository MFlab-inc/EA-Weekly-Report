# open-questions — しょうさんへの確認事項

記載ルール: SPECで判断できない事項のみ記録（HANDOFF §7）。回答をもらった項目は「決定」欄に記入し、SPEC/configへ反映後クローズする。

## Q1. FF翌週分が取得不可の場合の本則確定【Phase 0実測・重要】

- **事実**: 木曜時点で `ff_calendar_nextweek.json` は404。Web調査でも「nextweek系は存在しない」が通説で、全公開実装がthisweekのみ使用。thisweekの週境界切替は遅く（日曜13:00 GMTで前週データの報告例）、本番時刻（土曜08:06 JST＝金曜19:06 ET）のthisweekは確実に現行週。→ **対象週（翌週）の発言系イベントはFFから構造的に取得できない公算が大きい**。土曜朝の実測で最終確定する
- **確認したいこと**: 実測で確定した場合、SPEC §3.4の優先順3を本則として実装してよいか:
  1. 発言・会見・証言・入札は公式チェッカー（日銀・FRB・RBA・BLS・米財務省入札API等、SPEC §3.5を前倒し実装）で取得
  2. 補えない分は「発言イベントは直前に公式でご確認ください」の定型注記＋WARN
  3. 統計指標のクロス突合（§3.3）も翌週分については土曜時点でFF側データがないため実施不可 → 鮮度検証・定例欠落検知・公式チェッカー突合で代替
- **追加提案（任意）**: 月曜朝にFF thisweek（=対象週になった後）と公開済みレポートを事後突合する検証runを追加し、相違があればしょうさんへ通知（WordPress上で手修正できる）。採否をご判断ください

## Q3. data/cache（みんかぶ生HTML）のPublicリポジトリへのコミット保留【提案】

- **事実**: SPEC §3.6/§10はdata/cacheへの取得生データ保存（＝Publicリポジトリへのコミット）を規定。一方、みんかぶ規約は第三者提供目的の複製・再配信を禁止しており、許諾は確認中
- **提案**: 許諾確定まで、みんかぶ生HTMLはActions artifact（保持期間付き・非公開に近い扱い）のみに保存し、リポジトリには正規化済み台帳JSON（自作の抽出結果）だけをコミットする。FFフィードJSONのキャッシュコミットは低リスクだが、同様にartifact運用に揃えることも可能。許諾OK後にSPECどおりのcacheコミットへ移行
- **決定**: （未回答）

## Q5. FFレート制限を踏まえた本番取得設計【報告のみ・異議なければこのまま実装】

- **事実**: FFカレンダーエクスポートはネットワーク（IP）単位で5分2リクエスト。GitHub Actionsは共有IPのため、他者と衝突して「Request Denied」になり得る
- **実装方針**: 本番は thisweek.json を1リクエストのみ（形式併用しない）。Request Denied検知→間隔を空けて最大3リトライ→不能ならHOLD。保険cron（+35分）が実質的な再試行になる。Phase 0の土曜実測もthisweek/nextweekの2リクエストに抑制済み
