# セットアップ・並行運用開始 手順書（しょうさん向け）

対象: GitHub Web UIのみでの操作（コマンドライン不要。HANDOFF.md §運用方針どおり）。
所要時間の目安: 約15分。

前提: リポジトリ（MFlab-inc/EA-Weekly-Report）は作成済み・コードは全てpush済みです。残っているのは
「本番ワークフローを有効化する」「GitHub Pagesを有効化する」の2点と、その後の並行運用です。

## 手順1: 週次配信ワークフローを本番へ移設するPRをマージする

`weekly.yml`（毎週の自動生成本体）は、これまで本番の`.github/workflows/`ではなく
`workflows-draft/`に置いていました（誤って毎週動き出さないための安全策）。これを本番へ
移すPRをレビューしてマージしてください。

> **2026-08-17追記**: 最初のPR（#2）は実装全体をマージしましたが、`weekly.yml`自体の
> `workflows-draft/`→`.github/workflows/`への実際の移設が漏れていました（Claude側の
> 見落とし）。この移設漏れと、確認のご依頼を受けて検証した結果判明した保険cron
> （08:41 JST）の冪等ガード不備（台帳の`generated_at`が実行のたびに変わるため、
> 当初の実装では実際には二重コミットしてしまう構造だった）をあわせて、別PRで是正します。
> PR番号は本メッセージの後段でお知らせします。

1. GitHubでリポジトリを開き、上部タブの **「Pull requests」** を開く
2. 該当PRを開き、変更内容（`.github/workflows/weekly.yml`が新設され、`workflows-draft/weekly.yml`が削除される差分）を確認
3. 問題なければ緑色の **「Merge pull request」** ボタン → **「Confirm merge」** を押す

このPRがマージされると、以下の3ジョブが有効になります（`.github/workflows/weekly.yml`のコメント参照）:

| ジョブ | 実行タイミング | 内容 |
|---|---|---|
| `build` | 毎週土曜 08:06 JST（保険で08:41にも再実行） | 収集→台帳生成→レンダリング→監査→`output/`へコミット |
| `deploy-pages` | `build`成功直後 | `output/`配下のレポートをGitHub Pagesへ公開 |
| `monday-ff-cross-check` | 毎週月曜 08:23 JST | Forex Factoryとの事後突合（相違があれば失敗して通知） |

手動でいつでも起動することもできます（手順4参照）。

## 手順2: GitHub Pagesを有効化する

1. リポジトリの **「Settings」**（歯車アイコン）タブを開く
2. 左メニューの **「Pages」** を開く
3. **「Build and deployment」** → **「Source」** のプルダウンで **「GitHub Actions」** を選択する（「Deploy from a branch」ではありません。これを間違えると`deploy-pages`ジョブが失敗します）
4. 保存は自動です（プルダウンを選ぶだけで反映されます）

## 手順3: Actions権限を確認する

1. 同じ **「Settings」** → 左メニュー **「Actions」** → **「General」** を開く
2. 下の方の **「Workflow permissions」** で **「Read and write permissions」** が選択されていることを確認する（`build`ジョブが`output/`・`data/`をリポジトリへコミットするために必要）
3. 選択されていなければ選んで **「Save」**

### FRED_API_KEYについて（確認のみでOK）

米国GDP等の一部データ取得元（FRED = セントルイス連銀の経済データAPI）用のAPIキーです。
**既にtask #41のライブ検証で実際に使われて動作確認済みのため、新規登録は不要**です。念のため
**「Settings」→「Secrets and variables」→「Actions」** を開き、`FRED_API_KEY`が一覧にあることだけ確認してください。無ければClaudeに再登録の要否を相談してください。

## 手順4: 手動で1回動かして動作確認する

1. リポジトリの **「Actions」** タブを開く
2. 左側のワークフロー一覧から **「weekly-report」** を選ぶ
3. 右側の **「Run workflow」** ボタン → ブランチは`main`のまま →
   （**2026-08-29追記**: 「force_regenerate」というチェックボックスが表示されます。通常は
   チェック不要です。対象週が既に生成済みでもコード修正を反映して作り直したい場合のみ
   チェックしてください。手順6.5参照）→ 緑の **「Run workflow」** を押す
4. 数分待って、実行結果に緑のチェックマーク✅が付けば成功です（`build`→`deploy-pages`の順に走ります。`monday-ff-cross-check`は月曜のcronでのみ動くため、この手動実行では動きません）
5. 失敗（赤い✕）の場合は、該当runを開いてログを確認するか、Claudeへ「weekly-reportの手動実行が失敗した」と伝えてください

## 手順6: 並行運用（1〜2週間の目安）

rebuild-plan_v0.3.mdの方針どおり、いきなり本パイプラインへ切り替えるのではなく、
**現行Manus配信と本パイプラインの出力を1〜2週間突き合わせて検収**してください。

- 毎週土曜、上記プレビューURLで新しいレポートを確認する
- 現行Manus配信の内容と見比べ、掲載イベント・時刻・停止スケジュールに差異が無いか確認する
- 差異があれば（既刊側の掲載漏れの可能性も含め）Claudeへ共有してください。`docs/validate-scripts-guide.md`の方針により、新パイプライン側にしか無いイベントは「回帰」ではなく「既刊側の漏れの可能性」として個別に判断します
- 検収が済んだ時点で、現行Manus環境の停止時期を決定します（rebuild-plan §10-7）

### 月曜のFF事後突合が失敗した場合の見方

月曜08:23 JSTの`monday-ff-cross-check`が赤い✕になっている場合、FFフィードとの間で
発表時刻の相違が見つかっています（掲載漏れではなく「時刻がズレている疑い」の検知）。

1. **「Actions」** タブ → 失敗した`weekly-report`のrun → `monday-ff-cross-check`ジョブを開く
2. ログに相違の一覧（イベント名・台帳側の時刻・FF側の時刻）が出力されています
3. 画面下部の **「Artifacts」** から `discrepancy-report` をダウンロードすると、同じ内容がJSON形式で入手できます
4. 相違が実際の誤りだと判断した場合は、既に配信済みの記事を手動で訂正してください（自動訂正はしない設計です。SPEC §3.3）。判断に迷う場合はClaudeへ相談してください

## 手順6.5: 修正が本番へ反映されているかの確認（重要）

**2026-08-29追記**（しょうさん指摘を受けて追加。実際に起きた事故の再発防止）:

自動生成に反映されるのは **`main`ブランチのコードだけ** です。Claudeが作業ブランチ
（`claude/`で始まる名前）にコミット・pushしただけでは、土曜・月曜のcronは一切影響を
受けません。GitHub Actionsのスケジュール実行は常にデフォルトブランチ（`main`）の
コードを使う仕様のためです。

実際に、8/17のPRマージ以降に行われた一連の修正（役職ランク方式への再設計、PCE等の
未マッピング解消、BTC週末ガイドの追加等）が`main`へ統合されないまま数週間が経過し、
その間の土曜cronは「対象週の台帳が既に存在する」という誤判定（冪等ガードの不具合。
2026-08-29のPRで是正）によって静かにスキップし続け、配信済みレポートが8/17時点の
コードのまま更新されない、という事故が発生しました。

したがって、**「修正しました」という報告と「本番に反映されました」は別のことです。**
以下をチェックポイントにしてください。

- Claudeから修正の報告を受けたら、**「mainにマージ済みか」を確認する**（報告に
  PRリンクとマージ状況が含まれているはずです。含まれていなければ確認してください）
- 修正はPRとして提出されます。**マージするまでは本番へ反映されません。** マージ操作
  自体はしょうさんが行います（手順1と同じ「Merge pull request」ボタン）
- マージ後、次に土曜cronが発火するまで実際の反映を待つか、急ぎの場合は手順4の
  「Run workflow」を手動実行してください（`force_regenerate`にチェックを入れると、
  対象週が既に生成済みでも強制的に作り直せます。コード修正をすぐ反映させたい場合に使います）

## 手順7: 緊急時の止め方（並行運用中に問題が起きた場合）

自動生成が想定外の出力を出し続ける等、いったん自動実行を止めたい場合の手順です。
**コードの変更もPRも不要**で、画面操作だけで即座に止められます。

### 今後の自動実行（毎週土曜・月曜のcron）を止める

1. リポジトリの **「Actions」** タブを開く
2. 左側のワークフロー一覧から **「weekly-report」** を選ぶ
3. 一覧右上の **「...」**（縦三点リーダー、ワークフロー名の右）をクリック
4. **「Disable workflow」** を選ぶ
5. 画面上部に黄色い帯で「This workflow is disabled」と表示されれば停止完了です。以後、土曜・月曜のcronは一切発火しません（`workflow_dispatch`の手動実行ボタンも同時に押せなくなります）

再開したいときは、同じ場所に表示される **「Enable workflow」** ボタンを押すだけです（設定・履歴は失われません）。

### 今まさに実行中のrunを途中で止める

上記のDisableは「次回以降」を止めるだけで、今動いているrunはそのまま最後まで走ります。
今すぐ止めたい場合は:

1. **「Actions」** タブ → 実行中（黄色い●が回っている）のrunを開く
2. 右上の **「Cancel workflow」** ボタンを押す

### 止めた後、何が起きた/起きないか

- `output/`・`data/`へ既にコミット済みの内容や、GitHub Pagesに既に公開済みの内容は**自動では消えません**（Disableは「次を止める」だけで「過去を消す」ものではないため）。既に公開されたプレビューページの内容自体を取り下げたい場合は、`Settings → Pages`で**「Unpublish site」**を選んでください（再開時は手順2のSource設定をやり直せば復帰します）
- 一時的な停止なら、まずはDisableだけで十分です（現行Manus配信は本パイプラインと独立しているため、こちらを止めても既刊配信には影響しません）
- 何が起きたか判断に迷う場合や、恒久的に元の設計へ戻す判断が必要な場合はClaudeへ相談してください
