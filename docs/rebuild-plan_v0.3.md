## 3. 完全自動化に伴う仕様変更（重要・要承認）

一次情報照合を機械検査に置き換えることで、**掲載できる文言と担保できる品質の範囲が変わる**。ここが本再構築で最も重要な整理であり、以下は正直な表記への変更として必須となる。

### 3.1 出典表記の正直化【要選択】

現行レポートは「発表日時は一次情報で確認し」と明記し、各イベントに「一次情報：BLS」等を表示している。完全自動化後は毎週の公式ページ確認を行わないため、**この表現は掲載できない**（確認していないものに「確認済み」を付けない、という現行監査スキルの禁止事項に自ら抵触するため）。

新表記案（フッター・ヘッダー注記）:

> 発表予定・前回値・市場予想は民間カレンダー（fxshihyo.com、取得日時を自動記録）に基づき、独立ソース（Forex Factory）との自動突合および機械検査を行っています。公式発表による日程変更・時刻変更が反映されない場合があります。重要な取引判断の前には発表主体の公式情報をご確認ください。

各イベントの出典行の選択肢:
- 案A: 「参照：民間カレンダー値」に統一（最も正直・シンプル）
- 案B: 発表主体名（BLS・RBA等）は参考表示として残しつつ、「照合済み」を意味しない表記にする（例:「発表主体：BLS／日時・数値は民間カレンダー値」）

初期提案は**案B**（読者が公式を確認しに行く導線として発表主体名は有用なため）。

### 3.2 イベント別コメントの辞書化

現行の各イベント1行コメント（例:「声明の文言変化に注目」）はAIが毎週書いている編集文。完全自動化では**イベント種別辞書による定型文**に置換する（例: 政策金利→「政策判断と声明の文言を確認します」、CPI→「物価動向と金融政策見通しへの影響を確認します」）。辞書未登録イベントはコメント省略（推測で生成しない）。

### 3.3 機械検査で担保できること／できないこと（正直な線引き）

| 担保できる（自動検査） | 担保できない（自動化で失うもの） |
|---|---|
| 日付・曜日・日本時間換算の算術的正しさ | 公式ページとの個別照合（日程変更・臨時イベントの検出） |
| 取得データの鮮度（対象週と日付が一致するか） | 週の文脈を踏まえた編集判断・個別コメント |
| 2ソース間の日時・存在の一致（突合） | 民間カレンダー自体の誤りの完全検出（両ソースが同じ誤りなら通過） |
| 定例イベントの欠落検知（例: 雇用統計月の第1金曜欠落） | 時刻未公表イベントへの当日フォロー |
| 表示ポリシー違反（JST語・英語名・禁止セクション・免責欠落） | — |
| HTML構造・台帳整合・モバイル6幅レイアウト（現行資産） | — |

### 3.4 ソース間不一致・単一ソース依存の扱い【要決定・初期値提案】

- ★★★イベントで2ソースの日付または時刻（±0分）が不一致 → **HOLD**（重要イベントの誤時刻は実害が大きいため）
- ★★イベントで不一致 → 「時刻要確認」注記付きで掲載（時刻連動の停止目安には使わない、という現行原則を継承）
- 片方のソースにのみ存在するイベント → ★★★はHOLD、★★は注記付き掲載
- 閾値・扱いはPhase 1稼働後の実測で見直す（EA-Risk-Monitorの2段階方式と同じ考え方）

## 4. データソース設計と検証状況

### 4.1 一次候補: fxshihyo.com 日別ページ

`https://fxshihyo.com/ar/day{YYYYMMDD}.php`（現行フローが週次で使用中）。日本語イベント名・★重要度・前回値・市場予想が一度に取得でき、**表示・命名ポリシー（fxshihyo日本語表記を第一基準とする）とデータ源が一致する**ため、名寄せ辞書の維持が不要になる。これが第一候補である最大の理由。

### 4.2 実地確認結果（2026-08-13・本計画作成時）

- fxshihyo.comトップページを静的取得（web_fetch）したところ、**2019年1月のカレンダーデータが返却された**。現在のデータはJavaScriptによる動的読み込み、または取得側キャッシュの可能性がある（原因は未特定）。
- この観測から2つの設計要件が確定する:
  1. **鮮度検証バリデータを必須化**: 取得ページ内の日付が対象週と一致しない場合は即HOLD（古いデータでレポートを生成する事故を構造的に防ぐ）
  2. **取得方式の実測をPhase 0最優先項目とする**: 日別ページが静的HTMLで現行データを返すか、Actions上で実測。静的で取れない場合はPlaywrightヘッドレス取得へフォールバック（validate_mobile_headerで実績のある既存技術のため追加リスクは小さい）

### 4.3 突合ソース: Forex Factory 週次JSON

EA-Risk-Monitorのcalendar.jsで毎日稼働実績のあるフィード。既知の課題として**翌週分フィード（ff_calendar_nextweek.json）の404が観測されている**（EA-Risk-Monitor計画書§13）。土曜朝時点で翌週分が取得できるか（thisweekフィードの週境界がいつ切り替わるか）はPhase 0で実測する。取得できない場合の代替突合先はみんかぶFX（命名ポリシーの補完参照先でもある）。

### 4.4 利用規約・robots確認【Phase 0・しょうさん確認事項】

現行フローも同じページを週次取得しているため負荷実態は変わらない（週6ページ・低頻度）が、スクリプトによる自動取得の可否はサイトの利用規約で確認する。fxshihyo.comは「予定一覧の正確性を保証しない」旨を明記しているため、§3.1の免責と整合させる。

### 4.5 アクセス設計

取得間1.5秒待機（既存fetch.jsの流儀）・User-Agent明示・取得結果をリポジトリにキャッシュ保存（再実行時は当日キャッシュを優先し再取得しない冪等設計）・失敗時は3回リトライ後HOLD。

## 6. 成果物仕様

1. **WordPress貼り付け用HTML断片**: 現行validate_report.pyのルールを継承 — `html`/`head`/`body`/`script`/`style`/`form`・追跡タグ・外部JS禁止。したがって**新デザインも全インラインスタイルで構築**する（デザインモック作成時の必須制約）。
2. **監査用data属性**: `data-ea-event-id`・日時・重要度・件数属性等の現行体系を継承（検証スクリプト流用の前提条件）。
3. **プレビュー**: GitHub Pagesに同一断片をビューワーシェルに載せて公開。ページ冒頭に「配信可／配信保留」ステータスと生成日時を表示。
4. **受け渡し手順**（土曜朝・約5分）: Pagesプレビューで見た目確認 → リポジトリの`output/ea-weekly-YYYYMMDD.html`をRaw表示 → Ctrl+A → コピー → WordPressに貼り付け。

## 7. スケジュール設計（GitHub cron）

| 項目 | 設定 | 根拠 |
|---|---|---|
| 本番cron | `6 23 * * 5`（金曜23:06 UTC = 土曜08:06 JST） | 現行08:15配信の踏襲。混雑帯00:00–04:00 UTCの手前・人気分（0/5/15/30分）回避（EA-Risk-Monitor §19の実測知見を適用） |
| 保険cron | `41 23 * * 5`（土曜08:41 JST） | scheduledイベントdrop対策。冪等ガード（当週分がPUBLISH_READY済みなら即終了）で二重生成を防止 |
| 手動 | workflow_dispatch | 両cronがdropした場合・HOLD解消後の再実行用（Web UIから実行、既存Initワークフローと同じ操作） |

## 8. 検証ゲート（HOLD設計）

| 種別 | 検査 | 出自 |
|---|---|---|
| 流用 | 台帳静的検査（validate_ledger）・HTML×台帳照合（validate_report）・日付別カード監査（validate_daily_event_layout）・モバイル6幅（validate_mobile_header）・公開可否（publish_gate） | 現行資産 |
| 新設 | 鮮度検証（取得データ日付×対象週の一致。§4.2） | 本再構築 |
| 新設 | クロスソース突合・定例イベント欠落検知（§3.3・§3.4） | 本再構築 |
| 新設 | ポリシーlint（読者向け「JST」語・英語イベント名・禁止セクション・免責/新出典表記の存在確認） | 本再構築 |

HOLD時の挙動: Actionsのrunを失敗（赤）にし、`hold-report.json`に理由一覧を出力。`output/`は更新しない（前週分が残る＝古い週のHTMLを誤って貼るリスクがあるため、プレビューのステータス表示に「今週分は保留」と明示する）。Actions失敗はGitHubの標準通知メールで把握できる。対応: 理由を見て手動再実行、解消不能なら当週は手動作成（現行スキルをClaude Code用に移植した`.claude/skills/`が手動時の手順書を兼ねる）。

## 9. デザイン・内容構成の刷新方針（次ステップでモック確定）

制約: 全インラインスタイル（§6）・スマホ6幅（320〜414px）検証・WordPress断片。以下は候補であり、**モック2案の比較で確定する**。

- **週間俯瞰ビューの新設**: 曜日×時間帯で★★★を一望できるタイムライン/グリッドを冒頭に置き、「今週どこで止めるか」を10秒で把握できるようにする
- **タイムテーブルの情報密度改善**: 現行は同一注意文が日ごとに反復されている。日別カードは「要点1行＋イベントチップ」に圧縮し、共通注意は1箇所に集約
- **重要度によるメリハリ**: ★★★＝詳細カード、★★＝1行コンパクト表示
- **発表枠（同時刻束ね）表示の継承**（例: 21:30枠にCPI＋コアを束ねる）
- **配色・タイポの刷新**: 現行の緑系グラデーションからの刷新案と、ブランド継承案の2方向で比較
- 見出し名は仕様正本v2.0で改訂可（現行ポリシーの固定見出しに縛られない）

### 12.3 掲載（再配信）に関する規約上の論点【しょうさん確認事項・最重要】

みんかぶFXのページ規約に、営業利用および第三者提供目的での情報の転用・複製・再配信を禁止する条項を確認した。fxshihyo.comもrobots.txtで自動アクセスを不許可としている。

重要な整理: **この論点は自動化によって新たに生じるものではない**。現行の手動運用でも民間カレンダー値（前回値・予想値）をレポートに転載しており、掲載の可否という論点自体は従来から存在する。自動化が加えるのは「取得方法」（自動アクセスの可否）の論点のみ。

対応方針（2段構え・レポートは止めない）:
- **設計**: 前回値・予想値の表示を`config`のトグルで一括ON/OFFできる構造にする。取得元も差し替え可能な抽象化（collect.jsのソースアダプタ方式）とする
- **確認**: しょうさんからカレンダー運営元へ転載・自動取得の可否を確認（みんかぶ: 運営 株式会社ミンカブ・ジ・インフォノイド、問い合わせ窓口あり）。許諾が得られればみんかぶ主体＋数値表示ONで確定
- **代替（許諾が得られない場合）**: スケジュール・イベント名・重要度は Forex Factory週次フィード（EA-Risk-Monitorで稼働実績）＋自前の日本語名辞書＋自前の重要度規則（configで管理。EA-Risk-Monitorのwatch_eventsと同じ思想）で構成し、前回値・予想値は数値転載をやめて読者向けリンク誘導に切り替える。EAユーザーの一次ニーズ（いつ止めるか）はこの構成でも完全に満たせる
- FF週次フィードの利用条件・翌週分の土曜時点可用性（§4.3）も併せてPhase 0確認項目とする

なお本件についてClaudeは法的助言を行えないため、規約解釈に不安がある場合は運営元への直接確認を優先されたい。
