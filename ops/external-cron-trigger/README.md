# 外部cronトリガーツール（複数リポジトリ対応）

GitHub Actionsのscheduleトリガーの発火遅延（EA-Weekly-Reportで過去最大約5時間、
EA-Risk-Monitorでは実行の大半がdropという報告あり。特定リポジトリ固有の問題ではなく
GitHub Actions全体の既知の制約）への対策ツール。VPS等の常時稼働環境のタスクスケジューラから
このスクリプトを毎分（または短い間隔で）起動し、`targets.json`に登録した各リポジトリの
`workflow_dispatch`をGitHub側のscheduleとは独立に直接叩く。

対象リポジトリ側の`.github/workflows/*.yml`は無変更（`workflow_dispatch`は元々存在する
トリガーを使うだけ）。GitHub側の`schedule:`によるcronはそのままフォールバックとして残す。

背景・詳細な提案経緯は`docs/cron-trigger-reliability-proposal.md`（EA-Weekly-Report向けの
提案書）を参照。

## 設計方針

- **対象は`targets.json`で管理**。新しいリポジトリ・ワークフローを追加する場合は、この
  ファイルへ1エントリ追記するだけでよい（`trigger.mjs`自体の変更は不要）
- **スクリプトは1本のみ**。対象ごとにコピーは作らない
- **実行タイミングは対象ごとに`cron`フィールド＋`timezone`フィールドで指定**する
  （後述のcron書式参照）。VPS側のタスクスケジューラは「このスクリプトを毎分起動する」の
  1エントリのみで足り、対象を増やしてもタスクスケジューラ側の設定変更は不要

## targets.jsonの書式

```json
[
  {
    "id": "ea-weekly-report",
    "repo": "MFlab-inc/EA-Weekly-Report",
    "workflow": "weekly.yml",
    "ref": "main",
    "cron": "5,6,7,8,9 8 * * 6",
    "timezone": "Asia/Tokyo",
    "enabled": true,
    "note": "任意の説明文（起動しない）"
  }
]
```

| フィールド | 説明 |
|---|---|
| `id` | このツール内部での識別子（重複起動排除の状態管理キーに使う）。任意の英数字 |
| `repo` | `owner/repo`形式 |
| `workflow` | ワークフローファイル名（例: `weekly.yml`）またはワークフローID |
| `ref` | 起動対象のブランチ（通常`main`） |
| `cron` | `分 時 日 月 曜日`の5フィールド（GitHub Actionsのschedule cronと同じ意味・曜日は0=日曜〜6=土曜）。**`*`または半角カンマ区切りの整数リストのみサポート**（範囲`-`・ステップ`/`記法は非対応。単純な週次1回起動という用途には十分なため意図的に簡易実装にしている） |
| `timezone` | `cron`フィールドの分・時・曜日をどのタイムゾーンで解釈するかのIANA名（例: `Asia/Tokyo`） |
| `enabled` | `false`にすると、このエントリは一時的に無効化される（削除せずに一時停止したい場合に使う） |
| `pat_env_var`（省略可） | このターゲット専用のPATを使う場合、その環境変数名を指定する。省略時は共通の`EXTERNAL_TRIGGER_PAT`を使う（PAT運用方針は下記参照） |

### リトライ窓について

`cron`フィールドのminuteに複数の分をカンマ区切りで指定しておくと（例: `"5,6,7,8,9"`）、
最初に成功した分で当日分の状態が記録され、以降の分は自動的にスキップされる（`dueTargets`の
「本日は既に発火成功済み」判定）。これにより、ある分の実行がVPS側の一時的な不調や
GitHub API側の一時的なエラーで失敗しても、次の分で自動的にリトライされる簡易的な
冗長性が得られる。

## PATの運用方針（複数リポジトリを見据えて）

対象リポジトリが増えることを見越して、2つの方式を比較する:

| 方式 | セキュリティ | 運用の手間 |
|---|---|---|
| **(A) リポジトリごとに別PAT** | 漏洩時の被害範囲が1リポジトリに限定される（最も安全） | リポジトリの数だけトークンを発行・保管・期限管理する必要がある |
| **(B) 複数リポジトリを1つのfine-grained PATでカバー**（推奨） | fine-grained PATは「Repository access」で複数リポジトリを個別選択できるため、対象外のリポジトリへは依然として無効（「全リポジトリ」スコープにするわけではない）。被害範囲は「このツールが管理する全リポジトリ」に限られる | トークンの発行・保管・期限管理は1つだけで済む |

**推奨は(B)**。fine-grained PATは対象リポジトリを個別選択でき（「All repositories」を
選ばない限り）、"複数リポジトリ対応だが野放図に全権限化はしない"という要件を満たせる。
新しいリポジトリを追加する際は、`targets.json`への追記に加えて、GitHub側のPAT設定画面で
「Repository access」にそのリポジトリを追加する一手間が必要になる（トークンの再発行は
不要。既存トークンの権限範囲をWeb UI上で編集できる）。

管理対象のリポジトリ数が非常に多くなる、または一部のリポジトリだけ特に機密度が高い、
といった事情が生じた場合は(A)への切り替えも検討する（`pat_env_var`フィールドで
ターゲットごとに別の環境変数名を指定できるようにしてあるのはこの将来の切り替えに
備えたもの）。

## VPS側のセットアップ（概略。詳細な手順書はEA-Weekly-Report分のみ`docs/cron-trigger-reliability-proposal.md`に記載）

1. このディレクトリ（`ops/external-cron-trigger/`）をVPSへ配置する（このリポジトリをVPS上に
   クローンしておき、このディレクトリだけ使う形で問題ない）
2. PAT（前述）を環境変数`EXTERNAL_TRIGGER_PAT`としてVPSの実行環境に設定する（**リポジトリへは
   コミットしない**。VPS側のみで保持する）
3. VPSのタスクスケジューラ（cron/systemdタイマー等）へ、`node trigger.mjs`を毎分実行する
   エントリを1つだけ登録する
4. `targets.json`を配置・編集する（`enabled: true`の対象のみ起動される）
5. `state.json`（重複起動排除の状態ファイル）はスクリプトが自動生成する。VPS上のみに
   存在し、リポジトリへはコミットしない

## テスト

`test/external-cron-trigger.test.js`（このリポジトリの`npm test`に含まれる）で、cron式の
マッチング・タイムゾーン変換・重複起動排除ロジックを検証している。ネットワーク呼び出し
（`dispatchWorkflow`）は`fetchImpl`引数でモック可能な設計にしてあり、実際にGitHub APIを
叩くテストは無い。
